## 1. 一次有针对性的内存定位

先无训练子进程采样，列出物理总量/available/系统提交量及上限（可取得才记）、控制器/worker/子进程的 PID、PPID、启动时间、可执行文件、RSS、可用时 USS/private bytes，以及系统前 10 个内存占用进程。无权限字段写 UNKNOWN，不为取字段提权，不上传与项目无关的敏感命令行。

按阶段观察：轻控制器启动、训练 worker 启动、导入 torch 前后、模型/优化器及缓存加载、首个更新、稳定训练、终点评估、保存 checkpoint、trial 结束/worker 退出。首选复用旧日志；只补缺失的读数。资源日志约每 10 秒及状态边界一条，不建立高频 profiler 或整内存转储。

必须分清：
A. worker 未启动时就因外部程序占用没有足够 RAM；
B. 控制器/恢复驱动也导入 torch/transformers 或持有模型，与 worker 重复常驻；
C. 存在本项目多余 worker、未退出子进程、DataLoader worker 或缓存副本；
D. 单条 trial 的 RSS 随逻辑步持续增大，或跨 trial 累积；
E. 只有评估/保存阶段出现瞬时峰值。
RSS 有共享部分，不能把各进程 RSS 相加当作精确的独占物理占用，也不能简单用 available−RSS 预测启动结果。使用系统读数与阶段增量互相核对。

若外部程序是主因，列出名称/PID/占用并提示用户手动关闭；不 taskkill 所有 python、不关闭浏览器/IDE/WSL/虚拟机/系统进程。仅对本 runner 创建且能核验身份的已废弃 worker 做正常退出管理，禁止凭 PID 数字猜归属。

## 2. 只对测量确认的原因做最小修改

优先级如下；不存在的问题不修改，已修好的问题不重复重构。

### 轻控制器 + 一个训练 worker

如果控制器或恢复驱动已导入重框架，拆开导入路径：控制器仅使用标准库、现有 psutil 和小型状态记录，不导入 torch/transformers，也不经 package __init__ 或 parent helper 间接导入。模型与优化器只在唯一活跃训练 worker 中存在。

若当前已有等价结构，保留它；不是必须再新建一套调度平台。若存在跨 trial 残留，优先每条 trial 使用独立子进程，在写好小结果和可恢复 checkpoint 后退出，控制器确认退出再开始下一条。不要每步重启模型，也不要同时保留训练和 GPU 评估进程。

### 数据、结果和大对象

保持一个只读 uint32 memmap token 缓存。不要把 8.5M tokens 全部转成 Python list/int64 tensor，或者在每条 trial 重新保留全部原始 JSON 对象。只对当前 batch 转换；ID、顺序、cursor 与标签逐项验证不变。若已经实现 memmap，不重新准备数据。

确认 DataLoader 实際 num_workers=0、persistent_workers=False；若实现根本不使用 DataLoader，不增加它。对未使用且造成明显内存成本的 pin_memory/预取做实测后关闭，保持数值与数据顺序。

日志不要每步读全文件→append列表→重写历史；原始步记录 JSONL 追加，小 STATE 原子更新，统计流式做。不要把 Tensor/计算图或模型/optimizer 的深拷贝存入历史结果对象。scalar 用 detach/item，完整状态只保留当前必要对象。

评估串行且禁用梯度；不能保留全 logits。checkpoint 保存避免同时持有许多完整 CPU 快照；只有已安全完成的 optimizer step 边界可记为恢复点，不能丢掉梯度累积状态还声称逐步恢复一致。

## 3. 正确的暂停/释放/恢复，而不是低内存原地空等

当前配置下，启动新重 worker 前以 available ≥ 2.6 GiB 连续 3 次采样（间隔 10 秒）作为暂定恢复条件。这是参考截图的启动余量，不是给已运行 worker 每一步加上 2.6 GiB 门槛。运行期仍然 1.5 告警/1.0 硬停。

若具体测量表明初始化峰值还需更多余量，报告所需值；不要降低 1.0 硬线。资源指标用当前安装版本支持的 API，不升级 psutil 为了取新字段。

若运行中不足：停止发起新的更新。可安全完成时在 optimizer step 边界落盘；若保存本身会造成危险分配，就保留上一个有效 checkpoint、记录丢失逻辑进度与全部实际尝试。随后让本任务 worker 正常退出，只留轻控制器等待。不要让持有约 GiB 级模型/框架的进程一直等待一个必须由它退出才会恢复的余量。

沿用有限等待政策（每 5 分钟检查，最多原合同剩余时间或 2 小时，取更短），不得每次重启都重置等待和总预算。重启只有在源码/配置/数据/状态身份核对成功且资源满足时进行。

## 4. 验证后直接恢复原队列

本任务需要真实修复，不只交报告。工程补丁必须有源码 diff 和新的执行版本身份，历史 science/config/data 和台账不变。checkpoint 跨工程版本恢复使用明确允许的兼容性记录；禁止去掉哈希检查。

对改动补最小回归：数据流与cursor不变；无重复队列；单writer；暂停恢复状态完整；小样本更新在原容差内。新独立 smoke 最多 16 次 optimizer.step 尝试，计入原总上限，不另开不记账训练。

随后优先完成队列中下一条未完成 A1 trial，从最后合法 checkpoint 续到原终点，经历训练→评估→保存→worker退出。若余下 trial 足够，再观察下一条自然开工，核实跨 trial 没有残留增长。不要看到 1–2 步成功就宣布长期资源问题解决。

已完成的 31 条必须依据原始完整性校验复用；待完成条数以本地注册表为准。只有合法未完成项或中断项续跑。不能用新代码重新洗掉原始结果。

验收成功后依照既有 A1剩余→A1_select→A2→B→C→final_holdout 队列及条件继续，不扩网格。注意原阶段含可选分路，以活动合同为准，不能为资源问题擅自跳过对照或提前打开 holdout。
